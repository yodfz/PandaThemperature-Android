# 协议v1.1更新 - 开发计划

## 需求背景

温度计固件版本更新到v1.1，通讯协议文档更新，主要变更包括：

1. **新增电池电量特性**：支持查询设备电池电压（UUID: 12340026-...）

## 技术细节

### 1. 电池电量计算

根据文档，电池电压与电量百分比的关系：
- 假设 3.0V = 0%，3.6V = 100%
- 电量% = ((电压 - 3.0) / 0.6) * 100
- 限制在0-100%范围内

### 2. 历史数据格式兼容

**新格式（10字节）**：
- Timestamp: 4 bytes (uint32_t)
- Temperature: 2 bytes (int16_t, 0.01°C)
- Humidity: 2 bytes (uint16_t, 0.01%)
- Voltage: 2 bytes (uint16_t, 毫伏) ⭐ 新增

**旧格式（8字节）**：
- Timestamp: 4 bytes
- Temperature: 2 bytes
- Humidity: 2 bytes

**兼容策略**：
- 解析时检查数据包长度
- 如果数据包长度是8的倍数但不是10的倍数，按旧格式解析（电压为null）
- 如果数据包长度是10的倍数，按新格式解析

### 3. 设备名称兼容

支持以下设备名称：
- `PandaTemperatureEX`（新版本默认）
- `PandaTemperature`（旧版本）
- `yodfz-temp`（备用名称）
- `Panda`（前缀匹配）

### 4. 数据库迁移

由于使用 `fallbackToDestructiveMigration()`，数据库升级时会清空旧数据。这是开发阶段的可接受行为。

如果未来需要保留数据，需要：
1. 实现 `Migration` 类
2. 在 `AppDatabase` 中配置迁移策略
3. 将 `fallbackToDestructiveMigration()` 改为 `.addMigrations(...)`

## 注意事项

1. **向后兼容**：
   - 历史数据解析需要兼容旧格式（8字节）
   - 设备名称扫描需要兼容旧名称
   - 电池电量特性可能不存在（旧固件），需要检查特性可用性

2. **数据丢失**：
   - 数据库升级会清空旧数据（开发阶段可接受）
   - 如果生产环境需要保留数据，需要实现迁移策略

3. **测试重点**：
   - 新格式历史数据解析
   - 旧格式历史数据兼容性
   - 电池电量读取和订阅
   - 设备名称扫描（新旧名称）

4. **性能考虑**：
   - 电池电量订阅会增加通知回调，但影响很小
   - 历史数据解析增加2字节，性能影响可忽略
