# 历史数据增量获取功能开发 - 开发计划

## 需求背景

目前的历史数据获取功能每次都会获取设备端的所有历史数据，当数据量较大时，传输时间长、功耗高、效率低。

根据新的通讯协议，历史数据特性（UUID: 12340023-1234-5678-1234-56789abcdef0）现在支持**Write + Notify**权限，可以通过写入时间戳实现增量获取：

- **写入时间戳 0**：获取全部历史数据（向后兼容）
- **写入时间戳 > 0**：只获取时间戳大于该值的新数据
- **增量获取**：只传输新数据，大幅减少传输量和时间

## 实现方案

### 1. 数据库层扩展

#### 1.1 TemperatureRecordDao.kt
- 添加方法：`getLatestRecord()` - 获取最新的一条记录（用于获取最后时间戳）
- 已有方法 `getLatestRecords(1)` 可以复用，但需要添加专门的方法提高可读性

### 2. 业务逻辑层扩展

#### 2.1 MainViewModel.kt
- 添加方法：`getLastHistoryTimestamp(): Long` - 获取本地最后一条数据的时间戳（0 表示没有本地数据）
- 修改方法：`fetchHistory(lastTimestamp: Long = 0)` - 支持增量获取
  - 参数 `lastTimestamp`：本地最后一条数据的时间戳，0 表示获取全部
  - 实现流程：
    1. 先停止之前的通知（如果已启动）
    2. **写入时间戳**（4字节，小端序）到历史数据特性
    3. 等待写入完成（使用 `writeCharacteristic` 的异步回调）
    4. 启用历史数据通知
    5. 接收并解析增量数据
    6. 检测结束标志（0xFF），完成获取
- 修改方法：`initializeDevice()` - 在自动同步历史数据时使用增量获取
  - 获取本地最后一条数据的时间戳
  - 调用 `fetchHistory(lastTimestamp)`

#### 2.2 数据写入流程
- 使用 `BleManager.writeCharacteristic()` 的异步版本（带回调）
- 等待写入完成后再启用通知
- 确保操作顺序正确：停止通知 → 写入时间戳 → 等待完成 → 启用通知

### 3. 兼容性处理

- **向后兼容**：`fetchHistory()` 默认参数为 0，调用时不传参数仍获取全部数据
- **首次使用**：如果本地没有数据，传入 0 获取全部数据
- **增量同步**：如果本地有数据，传入最后一条的时间戳，只获取新数据

### 4. 错误处理

- 写入时间戳失败时，记录错误日志并停止获取
- 超时处理：保持现有的 60 秒超时机制
- 如果写入失败，自动降级为获取全部数据（可选）

## 技术细节

### 时间戳格式
- **类型**：`Long`（Unix 时间戳，秒）
- **写入格式**：4字节，小端序（Little-Endian）
- **特殊值**：`0` 表示获取全部历史数据

### 写入数据格式
```kotlin
val buffer = ByteBuffer.allocate(4).order(ByteOrder.LITTLE_ENDIAN)
buffer.putInt(lastTimestamp.toInt())
val timestampBytes = buffer.array()
```

### 操作顺序（重要）
1. 先停止历史数据通知（如果已启动）
2. 写入时间戳到历史数据特性（4字节，小端序）
3. **等待写入完成**（在 `onCharacteristicWrite` 回调中确认）
4. 启用历史数据通知
5. 接收并解析增量数据
6. 检测结束标志（0xFF），完成获取

### 获取最后时间戳逻辑
```kotlin
private suspend fun getLastHistoryTimestamp(): Long {
    val latestRecords = recordDao.getLatestRecords(1)
    return if (latestRecords.isNotEmpty() && latestRecords[0].timestamp > 0) {
        latestRecords[0].timestamp
    } else {
        0L // 没有本地数据或时间戳为0，获取全部
    }
}
```

## 注意事项

1. **操作顺序**：必须严格按照顺序执行（停止通知 → 写入时间戳 → 等待完成 → 启用通知）
2. **异步写入**：必须等待写入完成后再启用通知，使用 `CompletableDeferred` 等待回调
3. **错误处理**：写入失败时应记录错误并停止获取，避免无效的增量获取
4. **向后兼容**：保持现有调用方式不变，默认参数为 0（获取全部）
5. **状态管理**：确保在写入和通知过程中的状态标志正确管理
6. **超时机制**：保持现有的 60 秒超时机制，防止长时间等待

## 测试场景

1. **首次连接**：本地没有数据，应获取全部历史数据
2. **增量同步**：本地有数据，应只获取新的历史数据
3. **写入失败**：模拟写入时间戳失败，应正确处理错误
4. **无新数据**：如果设备端没有新数据，应快速收到结束标志
5. **大数据量**：测试增量获取在大数据量下的性能提升
