# 20260913 安卓端 BLE OTA 联调验收小结

> 范围：协议同步 + BLE OTA 客户端 + 真机联调（含 1.0.7 判决跑）。
> 详细设计过程见同目录 `20260913-固件协议同步与BLE OTA客户端-plan.md`，本文件只做验收口径的结论汇总。

## 0. 一句话结论

在真机 `PandaTemp_7086` 上完成了一次**版本号会变**的完整 OTA（1.0.6+0 → 1.0.7+0）：
App 侧状态帧由 `固件:v6` 变为 `固件:v7`，固件侧 SWD 读主槽 `ih_ver == 1.0.7+0`，
两侧独立事实对上，**客户端 OTA 全链路在真机上闭环**。

```
magic    = 96f3b83d   ✔
img_size = 144,928    ✔
ih_ver   = 1.0.7+0    ← 升级前 1.0.6+0，版本真的变了
PC = 0x24BF0（App 区）  VTOR = 0x8200  CFSR/HFSR = 0（无故障）
```

## 1. 做了什么（一句话一条）

**协议同步**
1. 修固件版本 → Profile 选型：消除「patch=6 被误判成 14 字节 V3 帧」的错配，真机确认选中 `V2(新固件)`。
2. 状态帧按 12 字节新格式解析：能力字节、墙钟可信位、可保留天数落到 `DeviceStatus`。
3. 历史记录新语义（`12340023` / `12340026`）在 V2 单条 12 B 口径下解析并入库。
4. `12340021` 采集间隔语义核对，与固件侧一致。

> **版本范围提醒**：以上协议事实基于固件 **1.0.6 / 1.0.7**（实时帧 6 字节、不上报电压）。
> **自固件 1.0.8 起**实时数据特征扩为 8 字节（`offset 6` = 小端 uint16 毫伏），并新增无效哨兵 `0xFFFF`；
> 1.0.6 / 1.0.7 仍为 6 字节，本文件结论对这两个版本继续成立。App 侧对哨兵/越界值的处理见
> `20260908-自动连接与电压展示-plan.md` 末节。

**BLE OTA 客户端（新增）**
5. 分层落地：`OtaImageParser`（MCUboot 头 + `ih_ver` + 整文件 SHA-256）、`OtaAuthKey`、`OtaMessages`（START/END/CANCEL/TRIGGER 报文）、`OtaStatusParser`、`OtaTransport` / `AndroidOtaTransport`（GATT 适配）、`OtaFlowController`（分片与 4 KiB 窗口）、`OtaRunner`（会话状态机）、`FirmwareOtaViewModel` + `FirmwareUpdateScreen`（UI）。
6. `BleManager` 补齐传输层必需能力：`onMtuChanged` 回调缺失修复、`writeCharacteristic` 异步结果回调、通知订阅异步化。
7. 流控键控在**设备 Status 上报的「已写入 Flash 连续偏移」**，而不是「已发送字节数」——用单测锁死。
8. 同步固件异步 START：等待超时 15 s 且**只认 `READY`**（`IDLE` 不算、ERROR 单独处理）；新增 `err=11 OVERRUN` 的重发 START 续传与重试预算。

**清理**
9. 固件版本显示口径统一到 `StatusBar`（`设备名 (vN) -- 版本字母`）。
10. 删除死代码 `ConfigModal.ActionButton`。
11. `MainViewModel` 提取式瘦身（只搬不动逻辑）。

**真机联调**
12. 用 1.0.7 镜像跑完整流程并完成判决（App 侧 v6→v7，固件侧 SWD 确认 `ih_ver=1.0.7+0`）。
13. 修复两个真机才暴露的客户端缺陷（见第 3 节）。

## 2. 真机实测指标

设备 `PandaTemp_7086`（MAC `D3:AE:E9:82:70:86`），MIUI / Android 13 + QTI 蓝牙栈。

| 指标 | 第一轮（1.0.6 镜像，145,590 B） | 判决轮（1.0.7 镜像，145,591 B） |
|---|---|---|
| MTU 协商 | App 请求 247 → 设备回 **128**（分片 125 B） | 同（128 / 125 B），**未回退到 65** |
| 状态帧 | **12 字节**；offset6=`0x06`（v6）、能力字节 `0x3F`、墙钟可信 | 同；升级后 offset6=`0x07`（v7） |
| Profile 选型 | `V2(新固件)` | `V2(新固件)` |
| START→READY | **1.07 s** | **1.07 s**（`START_READY_TIMEOUT_MS=15_000` 余量充足） |
| 传输耗时 / 速率 | 约 24 s ≈ **5 KB/s** | 约 57 s ≈ **2.55 KB/s** |
| 流控落点 | 已确认 144,896 / 已发送 145,590 | 已确认 **144,896** / 已发送 **145,591** |
| END→校验通过 | — | 约 16.7 s（含整镜像 SHA-256） |
| `err=11 OVERRUN` | **0 次** | **0 次** |
| TRIGGER → 断链 | 立即（GATT 133） | **5.0 s**（`特征写入失败: 133` + `设备已断开`） |
| 重启后重连 | 49 s 后自动重连成功 | 回首页后重连成功 |
| 重启后版本 | v6（未变，推送的是同一份镜像） | **v6 → v7** |

**关于 144,896**：= 566 × 256，是 256 B 页对齐的整页边界；尾部 694 B 由 `END` flush。两次跑落点一致，符合预期。

**关于速率差异**：判决轮慢一倍，logcat 同时段有 GMS/Finsky 密集 job，判断是手机后台负载而非协议问题（`err=11` 仍为 0，无任何 Data 写入失败）。

**关于 OVERRUN 的旁证**：判决轮 `12340051`（OTA Control）全程**只出现 3 次写**——START / END / TRIGGER，没有任何重发的 START，这本身就证明 OVERRUN 一次都没触发。

## 3. 修复的两个真机缺陷及根因

两个缺陷在 PC 客户端与单元测试里都复现不出来，只在真机（MIUI / Android 13 + QTI 栈）暴露。

### 3.1 `AndroidOtaTransport.writeData()`：第 2 片 Data 就被拒

- **现象**：App 报「升级失败：写入 OTA Data 失败（偏移 125）」，进度「已确认 0 / 已发送 125」；logcat 里 `12340052` 只有 1 次「特征写入成功」，**蓝牙栈无任何报错**。
- **根因**：原实现是 fire-and-forget，直接返回 `gatt.writeCharacteristic()` 的 Boolean。**同一特征同时只允许 1 个在途写**，上一片还没收到 `onCharacteristicWrite` 就发下一片时 API 直接返回 `false`——这是瞬时「忙」，不是链路错误，却被当成永久失败。
- **修法**：等写完回调再发下一片 + 忙重试（最多 5 次、退避 8 ms、单片超时 5 s；超时视为链路问题直接失败）。协议与业务语义未动，正确性仍由 `END` 的字节数 + 整镜像 SHA-256 兜底。

### 3.2 `OtaRunner.triggerUpgrade()`：`status=133` 被误判为触发失败

- **现象**（真机 logcat 原文）：
  ```
  11:30:20.028 E/BleManager(30029): 特征写入失败: 133
  11:30:20.028 D/BleManager(30029): 设备已断开
  11:30:20.028 D/MainViewModel(30029): [INFO] 设备已断开连接
  ```
  设备其实**已收到 TRIGGER 并立即复位**，链路被拉断导致 Android 报 `133 (GATT_ERROR)`，App 却判成「触发失败」。
- **根因**：`triggerUpgrade()` 把 TRIGGER 的写失败一律当失败，没考虑「写失败 + 链路断开」正是设备已复位重启的正常表现。
- **修法**：写失败后轮询链路，1.5 s 内 `isConnected()` 变 false ⇒ 判定**已成功触发**。
- **验证**：修复后同一场景 UI 显示「升级已触发。设备重启后请重新连接确认固件版本。」（`Phase.DONE`），不再报失败。

## 4. 已验证 / 未验证

### 已验证（有真机证据）

- MTU 协商结果 128、分片 125 B，未触发 65 回退路径。
- 状态帧 12 B 解析：版本号、能力字节、墙钟位、可保留天数，与固件侧一致。
- Profile 选型在真机上命中 `V2(新固件)`（修复前会误判 V3）。
- 异步 START 的实际耗时（1.07 s）与「期间设备不发任何通知」的行为。
- 完整传输 145 KB 级镜像，字节数与整镜像 SHA-256 校验通过，设备进入 `VERIFY`。
- 4 KiB 窗口键控在设备确认的 Flash 偏移，落点 144,896（整页边界）与预期一致。
- `END` 后设备停在 `VERIFY`，必须再点「立即重启并安装」（UI 已接，无需补代码）。
- TRIGGER 后设备真实断连重启；修复后 App 正确显示已触发。
- 重启后 App 自动/手动重连成功，状态帧上报新版本号，继续走 V2 Profile 与自动初始化。
- **1.0.7 判决跑：App 侧 v6→v7 与固件侧 SWD `ih_ver=1.0.7+0` 相互印证。**

### 未验证（本次没做，不要当成通过）

- **传输中途断电 / 拔电池**：只验证了正常路径，未做断电专项；`ERROR` 态与断点续传的行为未经真机扰动验证。
- **`err=11 OVERRUN` 的真实触发路径**：两轮真机 + 固件侧 PC 客户端 4 次传输**一次都没触发**，重发 START 的续传分支只有单测覆盖（FakeDevice 模拟），没有真机证据。
- **MCUboot 拒绝坏镜像的端到端取证**：未构造被篡改/未签名镜像验证「TRIGGER 后 MCUboot 拒绝、设备回退旧固件」这一路径，App 侧对应的错误呈现也未验证。
- **`CANCEL` 路径**：真机只走了 START→Data→END→TRIGGER，未测中途取消与取消后重发 START。
- **长时间稳定性 / 反复升级**：只各跑了一轮，未做连续多轮升级或长时间后台运行的稳定性观察。
- **多设备 / 其他安卓 ROM**：仅在一台 MIUI（Android 13 + QTI 栈）上验证；3.1 的「单在途写」行为在其他栈上可能表现不同。
- **低电量、弱信号、距离拉远等链路劣化场景**下的重试与降级。
- **非整页长度镜像**：144,896 是整页边界，尾部 flush 路径依赖 `END`；不同长度镜像的边界行为未逐一验证。
