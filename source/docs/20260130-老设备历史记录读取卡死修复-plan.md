# 老设备历史记录读取卡死修复-plan

## 需求背景

用户反馈老设备（V1固件）无法读取历史记录，会长时间卡死在读取历史记录界面。

## 问题分析

通过代码审查，发现以下问题：

### 1. 核心问题：V1/V2 设备的 HISTORY_INFO_CHAR 含义不同

`HISTORY_INFO_CHAR` 和 `BATTERY_CHAR` 使用相同的 UUID（`12340026-1234-5678-1234-56789abcdef0`）：
- **V1 老固件**：这个 UUID 可能用于电池电量特征（2字节），不是历史记录信息
- **V2 新固件**：使用这个 UUID 作为历史记录信息特征（8字节：总记录数 + 起始扇区 + 起始索引）

原代码仅通过 `isCharacteristicAvailable(BleConstants.HISTORY_INFO_CHAR)` 判断是否读取历史记录信息，导致：
1. 老设备可能存在这个 UUID（作为电池特征），检查返回 true
2. 读取到的数据格式不同（2字节电池数据 vs 8字节历史信息）
3. 如果数据被错误解析为历史记录信息，`expectedHistoryTotal` 可能变成一个非常大的错误值
4. 导致进度条永远无法完成，看起来像"卡死"

### 2. 缺少超时机制的 `CompletableDeferred.await()`
在 `fetchHistory()` 和 `finishHistoryFetch()` 中，多处使用 `CompletableDeferred.await()` 等待蓝牙操作完成，但没有超时机制。

### 3. 缺少 HISTORY_CHAR 可用性检查
在 `fetchHistory` 开始时没有检查 `HISTORY_CHAR` 是否可用。

## 实现方案

### 修改文件
- `MainViewModel.kt`

### 核心修复

1. **根据设备 Profile（V1/V2）判断是否读取 HISTORY_INFO_CHAR**
   - 只有 V2 固件（`usesCombinedRealtimeData == true`）才读取历史记录信息特征
   - V1 老固件跳过此步骤，`expectedHistoryTotal` 设为 null
   - 进度显示只显示接收数量，不显示总数

2. **添加超时机制防止永久挂起**
3. **前置检查 HISTORY_CHAR 可用性**

## 修改说明

### 修改文件
- `app/src/main/java/com/example/pandatemperature/ui/viewmodel/MainViewModel.kt`

### 具体修改

1. **根据设备 Profile 判断是否读取 HISTORY_INFO_CHAR**（核心修复）
   ```kotlin
   val isV2Firmware = currentDeviceProfile?.usesCombinedRealtimeData == true
   
   if (isV2Firmware && bleManager.isCharacteristicAvailable(BleConstants.HISTORY_INFO_CHAR)) {
       // V2 固件：读取历史记录信息
   } else {
       // V1 老固件：跳过，进度以接收数量为准
   }
   ```

2. **添加 `withTimeoutOrNull` 导入和超时常量**
   - `BLE_READ_TIMEOUT_MS = 5000L` - 读取特征超时
   - `BLE_WRITE_TIMEOUT_MS = 5000L` - 写入特征超时
   - `BLE_NOTIFY_TIMEOUT_MS = 5000L` - 启用/禁用通知超时

3. **前置检查 HISTORY_CHAR 可用性**
   - 如果设备不支持历史数据特征，提前返回并显示错误日志

4. **所有 BLE 操作添加超时机制**
   - 使用 `withTimeoutOrNull` 包装所有 `CompletableDeferred.await()` 调用

5. **错误恢复**
   - 启动通知失败后恢复实时数据订阅

6. **老设备进度显示**
   - 老设备跳过读取历史记录信息后，立即更新任务状态显示"已同步0条"
   - 让用户在同步开始时就能看到进度

7. **设置按钮显示条件修复**
   - StatusBar 中的设置按钮只在 `Connected` 状态显示
   - 修复 `Connecting` 状态时按钮显示但点击无效的问题

8. **老设备使用同步通知方法**（参考 release/1.0.0）
   - V1 老固件使用 `enableNotification()` 同步方法
   - V2 新固件使用 `enableNotificationAsync()` 异步方法
   - 与 release/1.0.0 保持一致的老设备处理方式

9. **架构优化：将版本差异抽象到 Profile**
   - 在 `ThermometerProfile` 接口中添加历史数据获取配置属性：
     - `supportsHistoryInfo: Boolean` - 是否支持历史记录信息特征
     - `useAsyncNotificationForHistory: Boolean` - 是否使用异步通知方法
   - V1Profile 实现：`supportsHistoryInfo = false`, `useAsyncNotificationForHistory = false`
   - V2Profile 实现：`supportsHistoryInfo = true`, `useAsyncNotificationForHistory = true`
   - ViewModel 中使用 Profile 配置，不再硬编码版本判断
   - 后续固件版本只需创建新 Profile 并配置相应属性，无需修改 ViewModel

10. **关键修复：老设备跳过暂停实时数据订阅**（2026-01-30 新增）
    - **问题**：新版本在 `fetchHistory` 开始时调用 `setRealtimeDataNotification(false)` 暂停实时数据订阅
    - **原因**：老版本（release/1.0.0）没有这一步，直接开始历史数据同步
    - **影响**：`setRealtimeDataNotificationV1(false)` 使用 `enableNotificationAsync` 停止温度和湿度通知，可能在老设备上导致蓝牙状态问题或超时
    - **修复**：
      ```kotlin
      // 只有新固件才暂停实时数据订阅
      // 老固件（useAsyncNotification = false）跳过此步骤
      if (useAsyncNotification) {
          addLog("正在暂停实时数据订阅，以优化传输通道...", LogType.INFO)
          setRealtimeDataNotification(false)
          kotlinx.coroutines.delay(500)
      }
      ```
    - **同步修改**：所有恢复订阅的地方也需要判断 `if (useAsyncNotification)`
      - `fetchHistory` 中的错误恢复分支
      - `finishHistoryFetch` 中的正常结束和异常恢复分支
