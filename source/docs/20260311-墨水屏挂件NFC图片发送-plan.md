## 需求背景

当前 PandaTemperature 项目主要围绕蓝牙温湿度/气压设备，通过 Android APP 展示实时/历史数据并做可视化分析。  
现在需要新增一个 **墨水屏挂件** 设备，它由 **STM32L010F4P6 + ST25DV16K 动态 NFC 标签 + 三色墨水屏** 组成，用于在营地/家庭场景下展示固定的图片信息（提示、二维码、天气卡片等）。

用户希望：

- 在「连接设备」列表中，始终看到一个固定设备 **「墨水屏挂件」**；
- 选择该设备后，首页主内容区域切换为 **墨水屏挂件操作界面**，但顶部的 `设备连接` 区域仍然保留，方便中断/返回；
- 在墨水屏挂件界面中：
  1. 从手机中选择一张图片；
  2. 在界面中预览一张 **128×250 像素、竖屏** 的图片框（逻辑分辨率），反映挂件实际显示区域；
  3. 点击“确认处理”后，将图片进行 **黑/白/红三色化 + 点阵混色处理**，生成适合三色墨水屏显示的位图，保证每个像素最终颜色确定为黑/白/红之一；
  4. 处理完成后，弹出一个 Modal，在其中显示处理好的图片，并提供“发送”按钮；
  5. 点击“发送”后，通过 NFC 与 **ST25DV16K I2C RFID 动态标签模块**通信，将图片发送给 STM32，由 STM32 刷新墨水屏。

本次开发先聚焦 **单向发送**（手机写入 → STM32 接收并刷新），不设计复杂的交互式 ACK/重传协议，仅保留必要的状态字段，后续可以迭代。

## 实现方案

### 一、整体架构设计

#### 1.1 模块划分

- **APP 端**

  - 设备管理层
    - 在现有设备抽象体系中，新增一个逻辑设备类型：`EInkPendantDevice`（墨水屏挂件），它不依赖蓝牙扫描结果，而是一个固定存在的“特殊设备”；
    - 设备“连接”更多是逻辑上的“当前操作目标选择 + NFC 可用性检测”，与蓝牙连接解耦。
  - UI 层
    - 连接设备列表：新增固定项 `墨水屏挂件`，带一个电子纸/小屏幕风格图标；
    - 首页内容区域：新增 `墨水屏挂件` 专用操作界面容器，例如 `EInkPendantScreen`；
    - Modal：新增 `EInkPreviewSendModal`，用于展示三色化后的图像并触发发送。
  - 图像处理层
    - 图片加载与裁剪/缩放模块；
    - 黑/白/红三色量化算法；
    - 点阵混色/抖动算法，保证边缘和灰阶过渡效果；
    - 图像编码模块，将三色图像编码为适合 STM32L010F4P6 解析的二进制数据。
  - NFC 传输层
    - 基于 Android NFC API 与 ST25DV16K 通信；
    - 在标签的 EEPROM 空间上实现分块写入协议（单向），确保在仅有 2KB 容量的前提下，能将约 8KB 的图片数据流式传输给 STM32。

- **设备端（STM32L010F4P6 + ST25DV16K + 墨水屏）**
  - ST25DV16K 动态标签
    - 通过 RF 接口和手机 NFC 通信，为图片数据提供 EEPROM 缓冲区（2KB），支持动态块读写；
    - 通过 I2C 接口与 STM32L010F4P6 通信，STM32 从其中按块读取图像数据。
  - STM32L010F4P6 控制器
    - 作为 I2C 主机读取 ST25DV16K 指定区域的数据，写入 MCU RAM 中的图像缓冲区；
    - 解析头部信息（宽高、总大小等），简单校验数据完整性（例如 CRC16 或长度校验）；
    - 调用墨水屏驱动，将接收到的黑/红双平面数据刷新到墨水屏。
  - 三色墨水屏
    - 目标分辨率：逻辑上按 **128×250 像素** 设计；
    - 支持黑/白/红三色显示，底层通过 SPI/GPIO 与 STM32L010F4P6 连接。

#### 1.2 数据流（高层）

1. 用户在「连接设备」中点击 `墨水屏挂件` → APP 将当前逻辑设备设置为 `EInkPendantDevice`，首页主内容区域切换为墨水屏挂件操作界面。
2. 用户选择图片 → APP 加载原始 Bitmap，并在界面中展示一张 128×250 的预览框，内部内容经过裁剪和缩放适配。
3. 用户点击“确认处理” → APP 在本地对图片做黑/白/红三色量化 + 点阵处理，生成最终的三色位图，同时编码为二进制数据。
4. 处理完成后，弹出 Modal 展示三色化效果图，用户点击“发送”。
5. 用户将手机靠近挂件 → 手机通过 NFC 与 ST25DV16K 建立通信，按约定的分块协议，将整包图像数据写入标签 EEPROM（流式多次写入）。
6. STM32L010F4P6 侧轮询/中断方式检测到新的图片任务，开始按块从 ST25DV16K 读取数据，写入本地 RAM 完整缓冲。
7. 图像数据接收完成且校验通过后，STM32L010F4P6 调用墨水屏驱动完成一次全屏刷新。
8. 刷新完成后，STM32 可选地在控制区写入一个简单状态值（例如“最后一次刷新成功/失败”），供后续调试使用（MVP 阶段 APP 不强依赖该状态）。

### 二、图像处理与编码方案

#### 2.1 分辨率与预览

- 逻辑显示分辨率：**宽 128 像素 × 高 250 像素**，竖屏方向；
- APP 预览框大小按 UI 设计适配，内部以 128×250 的像素网格逻辑渲染；
- 对于原始图片：
  - 先根据目标比例（128:250）进行裁剪，优先保证图像主体居中；
  - 然后缩放到 128×250 分辨率；
  - 最终作为后续三色化算法的输入。

#### 2.2 黑/白/红三色量化策略

目标：将任意彩色图片转换为黑/白/红三色，尽量保留对比度和重要信息，并利用点阵混色提升观感。

基本思路：

1. 将 RGB 像素转换到亮度/色度空间，例如计算：
   - 亮度 \(Y\)；
   - 红色分量 \(R\) 与 \(G,B\) 的差值（判断是否偏红）。
2. 针对每个像素应用如下决策逻辑（简化版本）：
   - 若亮度低于某个黑色阈值 → 判为 **黑色**；
   - 否则若红色通道明显高于绿色和蓝色（例如 \(R - \max(G,B)\) 大于某个阈值），且亮度中等 → 判为 **红色**；
   - 其余情况 → 判为 **白色**。
3. 为避免边缘与灰阶区域出现“生硬块状”：
   - 可以在灰度层面先做一次有序抖动（Ordered Dithering），把灰阶映射到黑白点阵；
   - 对偏红区域再叠加一层红色优先规则，使局部区域形成红色点阵效果；
   - 但 **最终每个像素只能是黑/白/红三者之一**，不出现多值混合。

#### 2.3 双平面编码（Black / Red Plane）

为了让 STM32L010F4P6 端和墨水屏驱动更简单，采用双平面 1bit 编码：

- **黑色平面（Black plane）**：1bit/像素
  - 1 表示黑像素；
  - 0 表示非黑（白或红）。
- **红色平面（Red plane）**：1bit/像素
  - 1 表示红像素；
  - 0 表示非红（白或黑）。
- 白色像素满足：Black=0 且 Red=0。

总像素数：  
`128 × 250 = 32000` 像素。

每个平面占用：  
`32000 / 8 = 4000` 字节。

整张图片数据大小约为：

- 黑平面 4KB + 红平面 4KB ≈ **8KB**。

该大小远大于 ST25DV16K 的 2KB EEPROM 容量，因此传输策略必须是 **“分块写入 + STM32L010F4P6 流式读取到 RAM”**，而非一次性保存在标签内。

#### 2.4 图像数据包结构（逻辑）

APP 侧构造的完整图片数据包（在逻辑上）可设计为：

- Header（固定或半固定长度）
  - Magic：2 字节，例如 `0x45, 0x49`（“EI” 表示 E-Ink）；
  - Version：1 字节（例如 0x01）；
  - Width：2 字节（小端，128）；
  - Height：2 字节（小端，250）；
  - Format：1 字节（bit0=黑平面存在，bit1=红平面存在 等）；
  - TotalBytes：4 字节，完整图像数据区字节数（例如 8000）；
  - ChunkSize：2 字节，每块业务数据大小，例如 256；
  - TotalChunks：2 字节，块数量，`ceil(TotalBytes / ChunkSize)`；
  - CRC16：2 字节，对整个数据区的校验值（可选，MVP 可不严格依赖）；
  - 预留：若干字节，后续可扩展显示模式等。
- Data 区
  - 黑平面数据（先行优先或列优先，由 STM32 与 APP 约定）；
  - 红平面数据。

实际写入 ST25DV16K 时，会把 Header 和 Data 按块拆分写入不同 EEPROM 区域，不要求数据包在标签上完全连续。

### 三、NFC 传输协议与 ST25DV16K 使用方案（单向发送）

> 重要说明：ST25DV16K 的 EEPROM 容量（约 2KB）远小于整张图片数据（约 8KB）。因此 APP 侧**不能**在不做任何反馈的情况下“连续覆盖式写入”，否则 STM32 可能尚未读走上一块数据就被覆盖，导致花屏/缺块。
>
> 本计划的 MVP 传输协议采用 **Stop-and-Wait（单块缓冲 + 最小流控）**：
>
> - 数据仍然是“手机写入 → STM32 读取并刷新”的单向业务流；
> - 但需要 STM32 通过 I2C **写回一个极小的进度字段**（`rxConsumedIndex`），用于告诉 APP “上一块已成功读走，可以写下一块了”；
> - 不引入复杂的块级重传与 ACK 消息体，仅做必要的“避免覆盖”。

#### 3.1 存储区域规划（建议）

参考 ST25DV16K 的典型分块方式，将 EEPROM 空间划分为：

- **控制/状态区**（例如前若干个 Block，建议固定地址范围）

  - 关键字段：
    - `magic`：标识是否存在有效任务；
    - `session_id`：会话号（APP 每次发送自增），用于“失败后直接换图重发”时快速切换上下文，避免串包；
    - `tx_state`：APP 发送状态，如 IDLE / SENDING / DONE / ABORT；
    - `rx_state`：STM32 接收/处理状态，如 IDLE / RECEIVING / APPLYING / OK / ERROR；
    - `width` / `height` / `total_bytes` / `chunk_size`；
    - `tx_chunk_index`：APP 当前写入的数据块序号；
    - `tx_chunk_len`：本块有效字节数（最后一块可能小于 chunk_size）；
    - `rx_consumed_index`：STM32 已成功读走的数据块计数（或“下一块期待序号”，与 STM32 约定一致）；
    - `crc16`：整体校验值（可选）。
  - 该区由 APP 一次性写入/更新，STM32L010F4P6 读取解释。
  - 其中 `rx_consumed_index` 与 `rx_state` 由 STM32 侧写回，作为最小流控与结果提示；APP 可选择读取以展示进度/错误。

- **数据缓冲区**
  - 用于写入实际图像数据块（Chunk）。
  - MVP 采用 Stop-and-Wait：数据缓冲区**只需要容纳 1 个 chunk**（例如 256 字节或 512 字节），APP 写入一块后等待 STM32 消费确认，再写下一块。
  - 后续若需提速，可扩展为滑动窗口（一次容纳多块），但不在本期范围。

#### 3.2 单向发送流程（APP 视角）

1. **准备阶段**
   - APP 完成图像三色化和编码，得到完整数据包；
   - 按配置的 `chunk_size`（例如 256）划分为 N 个 Chunk。
2. **靠近设备 & 建立 NFC 会话**
   - 用户在 Modal 中点击“发送”，APP 检测 NFC 可用性；
   - 提示用户将手机贴近挂件，开始 NDEF/Raw 通信。
3. **写入控制区（头部信息 + 新 session）**
   - APP 生成新的 `session_id`（相对上次 +1，循环即可）；
   - 写入控制区字段：magic、session_id、tx_state=SENDING、width、height、total_bytes、chunk_size、total_chunks、crc16 等；
   - 将 `tx_chunk_index=0`，`tx_chunk_len=chunk_size`（最后一块在写入时再更新）。
4. **循环写入数据块（Stop-and-Wait 最小流控）**
   - 对每个 `chunk_index`：
     - APP 先读取控制区的 `rx_consumed_index`，等待其达到约定值（表示 STM32 已消费上一块，可以写下一块）；
     - 将本块数据写入数据缓冲区（固定地址范围）；
     - 更新控制区 `tx_chunk_index` 与 `tx_chunk_len`，表示“本块已准备好”；
     - 若 NFC 断开/写入失败，APP 设置 `tx_state=ABORT`（能写则写），并提示用户重试。
5. **结束标记**
   - 所有块写入完成后，APP 将 `tx_state=DONE`；
   - APP 可选择读取 `rx_state` 展示最终结果（OK/ERROR），但 MVP 阶段不强依赖，提示“发送完成，请稍候等待设备刷新”即可。

> MVP 阶段，为了简化逻辑，不做复杂的块级重传：遇到任意 NFC 读写失败即中断并提示用户重试。最小流控仅用于避免覆盖，提高成功率与一致性。

#### 3.3 STM32L010F4P6 侧接收流程（简要）

1. **空闲轮询/中断检测**
   - STM32L010F4P6 通过 I2C 定期读取 ST25DV16K 控制区；
   - 若检测到 `magic` 有效且 `tx_state=SENDING`，或 `session_id` 发生变化，则认为有新任务：
     - 立即重置本次接收进度；
     - 写回 `rx_state=RECEIVING`，并将 `rx_consumed_index` 复位为 0（或约定的初值）。
2. **解析头部信息**
   - 读取 width/height/total_bytes/chunk_size/total_chunks 等；
   - 根据 total_bytes 在 RAM 中分配缓冲区（至少约 8KB）；
   - 若内存不足或参数异常，则写入 `status = ERROR`，本次任务放弃。
3. **按块读取数据（Stop-and-Wait）**
   - 对 chunk_index 从 0 到 total_chunks-1：
     - 等待控制区 `tx_chunk_index==chunk_index`（表示 APP 已准备好本块）；
     - 通过 I2C 从“数据缓冲区固定地址”读取本块数据到 MCU RAM 的对应位置；
     - 写回 `rx_consumed_index`（例如写入 chunk_index+1），通知 APP 可以继续写下一块。
4. **校验与解析**
   - 若使用 CRC16，则对全部数据区计算 CRC，与控制区中的 CRC 对比；
   - 校验通过则进入刷新流程，否则写入 `status = ERROR`。
5. **刷新墨水屏**
   - 将缓冲区中的黑平面与红平面数据转换为墨水屏驱动期望的格式；
   - 执行一次全屏刷新；
   - 刷新完成后，将控制区 `rx_state` 设为 `OK`；失败则设为 `ERROR` 并写入 error_code（可选）。

#### 3.4 失败后重试/换图再次传输（会话覆盖）

- APP 每次点击“发送”都创建新的 `session_id` 并写入控制区。
- STM32 检测到 `session_id` 变化后，立即丢弃旧会话的接收进度并重置状态，保证“失败后直接换图重发”不会串包。
- 若 APP 发送中断（Tag 离开/超时），尽量写 `tx_state=ABORT`；STM32 看到 ABORT 后回到 IDLE，保持当前屏幕不变。

### 三点五、STM32L010F4P6 固件开发指南（MVP）

本章节用于指导 STM32 侧实现“读取 ST25DV16K 控制区 + Stop-and-Wait 流式接收图片 + CRC 校验 + 刷新墨水屏”的最小可用固件。  
目标原则：**不刷半张图**、**失败可直接换图重发**、**协议字段尽量稳定**。

#### 3.5.1 模块划分建议

- **st25dv16k 驱动层（I2C）**
  - 负责按地址读写 ST25DV16K 的 EEPROM（或动态寄存区/邮箱，按你硬件连接与配置决定）
  - 提供：`read(addr, buf, len)` / `write(addr, data, len)`（内部处理页写、写入等待、NACK 重试等）
- **nfc_transfer 协议层**
  - 负责解析控制区结构、管理 `session_id/tx_state/rx_state/rx_consumed_index`
  - 负责 Stop-and-Wait 的“等待本块 ready → 读取 dataBuffer → 写回 consumedIndex”
- **image_buffer 图像缓存层**
  - 负责在 RAM 中存放整包 payload（黑平面 + 红平面），并提供给墨水屏驱动
- **eink 驱动层**
  - 提供：`eink_init()` / `eink_display(blackPlane, redPlane, w, h)` / `eink_busy_wait()` 等

#### 3.5.2 控制区结构（与 APP 对齐）

控制区为定长字节数组（建议 128 字节），小端序。字段偏移如下（与 APP 侧 `EInkNfcProtocol` 对齐）：

- **0..1**：magic = `0x45 0x49`（"EI"）
- **2**：version = `0x01`
- **3**：`session_id`（u8，APP 每次发送自增，循环）
- **4..5**：`width`（u16，MVP 固定 128）
- **6..7**：`height`（u16，MVP 固定 250）
- **8**：`format`（u8，bit0=blackPlane，bit1=redPlane；MVP 固定 0x03）
- **9**：`tx_state`（u8：0=IDLE，1=SENDING，2=DONE，3=ABORT）——APP 写
- **10**：`rx_state`（u8：0=IDLE，1=RECEIVING，2=APPLYING，3=OK，4=ERROR）——STM32 写回
- **11**：`error_code`（u8）——STM32 写回（可选，但建议保留）
- **12..15**：`total_bytes`（u32，MVP=8000）
- **16..17**：`chunk_size`（u16，MVP 建议 256）
- **18..19**：`total_chunks`（u16）
- **20..21**：`crc16_ccitt`（u16，poly=0x1021 init=0xFFFF，对 payload 全部字节）
- **22..23**：`tx_chunk_index`（u16）——APP 写（表示当前 dataBuffer 对应的 chunkIndex）
- **24..25**：`tx_chunk_len`（u16）——APP 写（最后一块可能小于 chunk_size）
- **26..27**：`rx_consumed_index`（u16）——STM32 写回（已成功消费的 chunk 数，建议写成“下一块期待 index”，即 chunkIndex+1）

> 建议 STM32 对 version 做兼容处理：若 magic 不符则直接忽略；version 不符则置 `rx_state=ERROR` 并写 `error_code=VERSION_UNSUPPORTED`。

#### 3.5.3 ST25DV16K EEPROM 区域规划（MVP 固定）

由于不同标签 block 大小可能不同，固件侧建议按“字节地址”规划，再由驱动适配“块/页”。  
本项目 **Android 与 STM32 侧统一采用同一份布局常量**（Android：`St25dvEInkLayout`），MVP 定稿如下：

- **Control 区**
  - 起始地址：`0x0000`
  - 长度：`128B`（`0x0000 ~ 0x007F`）
- **DataBuffer 区**
  - 起始地址：`0x0080`
  - 长度：`256B`（`0x0080 ~ 0x017F`，与 `chunk_size=256` 对齐）

> 若你希望 DataBuffer 更大（比如 512B），只要同时调整 `chunk_size` 与 DataBuffer 大小即可；Stop-and-Wait 仍然成立。

#### 3.5.4 接收状态机（推荐实现）

建议 STM32 采用轮询（或 ST25DV GPO 中断）驱动一个状态机，伪代码如下：

1. **IDLE**
   - 读取 control（最低频率即可，如 20~50ms）
   - 若 `magic` 有效且 `tx_state==SENDING`：
     - 若 `session_id` 与本地记录不同：进入 NEW_SESSION
     - 否则：进入 RECEIVING（断点续传可选，MVP 可不做）
   - 若 `tx_state==ABORT`：清空本地会话记录，保持 IDLE
2. **NEW_SESSION**
   - 记录 `session_id`
   - 校验 width/height/format/total_bytes/chunk_size/total_chunks 合法性
   - 分配/准备 payload 缓冲（至少 `total_bytes`，MVP 8000）
   - 写回：
     - `rx_state=RECEIVING`
     - `rx_consumed_index=0`
     - `error_code=0`
   - 进入 RECEIVING
3. **RECEIVING**
   - 对 `chunkIndex` 从 0 到 `total_chunks-1`：
     - 等待 `tx_chunk_index == chunkIndex`（并且 `tx_state==SENDING` 且 `session_id` 未变化）
     - 从 DataBuffer 区读取 `tx_chunk_len` 字节到 `payload[chunkIndex*chunk_size ..]`
     - 写回 `rx_consumed_index = chunkIndex + 1`
     - 若过程中检测到 `tx_state==ABORT` 或 `session_id` 变化：立即退出到 IDLE / NEW_SESSION
   - 全部接收后进入 VERIFY
4. **VERIFY**
   - 计算 payload CRC16-CCITT，与 `crc16_ccitt` 对比
   - 若失败：
     - 写回 `rx_state=ERROR`，`error_code=CRC_MISMATCH`
     - 回到 IDLE（保持屏幕不变）
   - 若成功：进入 APPLYING
5. **APPLYING**
   - 写回 `rx_state=APPLYING`
   - 调用墨水屏刷新（必须等 busy 结束）
   - 成功：写回 `rx_state=OK`
   - 失败：写回 `rx_state=ERROR`，`error_code=EINK_FAIL`
   - 回到 IDLE

#### 3.5.5 CRC16-CCITT 参考实现（固件侧）

- 参数：`poly=0x1021`，`init=0xFFFF`，无反射，结果 16bit
- 输入：payload 全部字节（黑平面 4000B + 红平面 4000B）

> APP 侧已按此算法计算并写入控制区的 `crc16_ccitt`。

#### 3.5.6 图像数据在 payload 中的布局（与 APP 对齐）

payload 结构（无额外 header）：

- `payload[0 .. 3999]`：Black plane（1bpp）
- `payload[4000 .. 7999]`：Red plane（1bpp）

位序约定：**每字节 MSB 优先**（第 0 个像素对应 bit7）。像素顺序：从左到右、从上到下线性递增。

> 若你墨水屏驱动需要不同的位序/扫描方向，建议在 STM32 侧做一次转换（或直接把驱动层改成支持该布局），但**协议侧不要轻易改**，以减少联调成本。

#### 3.5.7 错误码建议（MVP 可选）

仅用于调试与 APP 提示，可先定义：

- `0x01`：VERSION_UNSUPPORTED
- `0x02`：PARAM_INVALID
- `0x03`：NO_MEMORY
- `0x04`：CRC_MISMATCH
- `0x05`：EINK_FAIL
- `0x06`：I2C_READ_FAIL
- `0x07`：I2C_WRITE_FAIL

#### 3.5.8 调试与联调建议

- **串口日志**：打印 session_id、chunkIndex、rx_consumed_index、CRC 结果、刷新耗时。
- **控制区回写**：在 ERROR 时写 `rx_state=ERROR + error_code`，方便 APP/现场快速定位。
- **超时策略（建议）**
  - 等待 `tx_chunk_index` 超时（例如 3~5s）：回到 IDLE（认为手机离开）
  - 接收中检测到 `session_id` 改变：立即切新会话（支持“失败后直接换图重发”）

### 五、后续优化方向：FTM（Fast Transfer Mode）方案草案

> 说明：本节为「下一阶段」的协议演进方案，目前代码仍使用 EEPROM 区 + 自定义 Stop‑and‑Wait 协议（CONTROL_ADDR/DATA_ADDR）。当当前方案稳定后，可再评估是否升级到 FTM。

#### 5.1 ST25DV16K FTM 简介

- **FTM/Mailbox RAM**：ST25DV16K 内部带有一块约 256 字节的 RAM Mailbox，用于 NFC 和 I2C 之间的高速数据交换。
- **关键差异**：
  - 现在方案：Android 读写用户 EEPROM (`0x0000` 控制区 + `0x0080` 数据区)，STM32 通过 I2C 轮询 EEPROM；
  - FTM 方案：Android 读写 Mailbox RAM，STM32 通过 Mailbox/FTM 寄存器在 **有数据时再去 I2C 读 256B**，平时无需频繁轮询 EEPROM。
- **优势**：
  - 数据不经过慢速 EEPROM，FTM RAM 的读写延迟更小；
  - I2C 访问次数减少、时间更短，减少对 RF 会话的打断，缓解「IO 异常」「Tag Lost」问题；
  - 更适合后续扩展为更大数据量（比如将来固件更新）。

#### 5.2 FTM 版 Stop‑and‑Wait 协议草案

- **基本思路**：
  - 仍然保持「一块最多 256 字节、Stop‑and‑Wait + `rxConsumedIndex`」的大框架；
  - 只是把「块数据」从 EEPROM `DATA_ADDR` 挪到 Mailbox RAM；
  - 控制字段可以：
    - 方案 A：仍放在 EEPROM 控制区（兼容当前 STM32 状态机）；
    - 方案 B：控制字段也放到 Mailbox 或 ST25DV 自带的 FTM 状态寄存器中（需要完全重写状态机）。
- **Android 侧（FTM 草案）**：
  1. 初始化时，写入控制区（或通过自定义命令）通知 STM32 即将开始新会话：`session_id` / `total_bytes` / `chunk_size` / `total_chunks` / `crc16` 等；
  2. 对于每个 `chunkIndex`：
     - 等待 `rxConsumedIndex == chunkIndex`（仍然通过控制区或 Mailbox 中的字段判断）；
     - 调用 ISO15693 + FTM 命令，将当前 256B 数据写入 Mailbox RAM；
     - 设置标志位（例如写入「本块 ready」的控制字段），触发 ST25DV Mailbox 中断 / GPO 变化。
- **STM32 侧（FTM 草案）**：
  1. 将 ST25DV 的 FTM GPO 引脚接到 STM32 的一个 EXTI 引脚；
  2. 当 Mailbox 有新消息时，GPO 触发中断/标志：
     - 中断服务里仅设置标志位，主循环中调用一次 Mailbox 读函数，读出 256 字节块；
     - 按当前 `g_expected_chunk` 写入 EPD RAM / 临时缓冲，并更新本地 CRC；
     - 把 `rxConsumedIndex` 写成 `g_expected_chunk + 1`，并清除 Mailbox 标志位；
  3. 当所有块接收完毕且 CRC 匹配时，刷新屏幕并进入 DeepSleep。
- **时序特点**：
  - STM32 不再「定时轮询」ST25DV，而是「被 Mailbox/GPO 事件唤醒」；
  - I2C 在每次块接收时只做一次 256B Mailbox 读 + 少量控制位更新，RF 窗口更完整。

#### 5.3 当前方案与 FTM 迁移的差异点

- **当前实现**：
  - Android：`St25dvEInkLayout.CONTROL_ADDR/DATA_ADDR`，ISO15693 读写 EEPROM；
  - STM32：`NFC_Transfer_Poll()` 定时 `ST25DV16K_ReadMem/WriteMem` 访问 EEPROM。
- **迁移到 FTM 需要的改动（概要）**：
  - Android：
    - 新增 FTM 相关的 ISO15693 命令封装（Mailbox 读写）；
    - 将图片块写入 Mailbox RAM，而不是 EEPROM 数据区；
    - 控制字段可保持兼容（仍写在控制区），或跟随迁移到 Mailbox。
  - STM32：
    - 在 `nfc_transfer.c` 中引入 ST25DV 的 Mailbox/FTM API；
    - 使用 GPO/中断方式监听「有新 Mailbox 数据」事件，按事件驱动读取块数据；
    - 在事件处理完成后写回 `rxConsumedIndex` 等控制字段，保持 Stop‑and‑Wait 语义不变。

### 七、FTM 版 0xCA 墨水屏图片分包协议（Android → STM32）

> 本节在前面 FTM 草案基础上，**结合 ST 官方 0xCA Fast Write Message 帧格式**，给出实际落地到墨水屏图片发送的字节级协议定义，供 Android 与 STM32 两侧严格对齐。

#### 7.1 外层 ST25DV FTM 报文结构（Android 侧）

Android 通过 `NfcV.transceive()` 发送一帧 FTM 时，完整报文为：

- Byte0：`Flags = 0x02`（高数据速率，非寻址模式，MVP 不传 UID）
- Byte1：`Cmd = 0xCA`（Fast Write Message）
- Byte2：`IC Mfg Code = 0x02`（ST 固定）
- Byte3：`LenByte = userPayload.length - 1`（长度减 1）
- Byte4..：`userPayload`（自定义业务负载）

其中 `userPayload` 为本协议定义的“内层负载”，由 Android 封装、STM32 在 Mailbox RAM 读取并解析。

#### 7.2 内层 userPayload 统一结构

为兼顾图片头信息与数据块，两类业务帧统一采用以下结构：

- Byte0：`CMD`（1B）
  - `0x01`：图片头帧（Header Frame）
  - `0x02`：图片数据帧（Data Frame）
- Byte1..2：`SEQ`（2B，小端序，`SEQ_L` 在前）
  - 头帧固定 `SEQ = 0`
  - 数据帧从 `1` 开始递增，每帧对应一个连续块
- Byte3：`FLAGS`（1B）
  - Bit0：`LAST_FRAME` 标志（仅对 Data Frame 有意义）
    - `0`：后面还有数据帧
    - `1`：这是最后一个数据帧
  - 其它 bit 预留，当前置 0
- Byte4..N-2：`DATA`（变长业务数据）
- ByteN-1：`CRC8`（1B）
  - 对本帧的 `CMD | SEQ_L | SEQ_H | FLAGS | DATA...` 做 CRC8 校验

Mailbox 总容量为 256B，每帧最多 256 字节。扣除固定 1+2+1+1=5 字节头尾，**DATA 理论上限为 251B**。  
为便于实现与对齐，MVP 约定：

- `FTM_CHUNK_DATA_SIZE = 240` 字节
- 即 Data Frame 的 DATA 区最多 240B，最后一帧小于等于 240B

#### 7.3 头帧（CMD=0x01, SEQ=0）的 DATA 内容

头帧 DATA 区承载整张图片的信息，结构如下（均为小端）：

- Byte4..5：`Magic` = `0x45, 0x49`（ASCII "EI"，E-Ink）
- Byte6：`Version` = `0x01`
- Byte7..8：`Width`（u16，MVP 固定 128）
- Byte9..10：`Height`（u16，MVP 固定 250）
- Byte11..14：`TotalBytes`（u32，完整图片字节数，MVP=8000）
- Byte15..16：`ChunkSize`（u16，固定为 240）
- Byte17..18：`TotalChunks`（u16，后续数据帧数量）
- Byte19..20：`Crc16Ccitt`（u16，对全部 `TotalBytes` 图像数据做 CRC16‑CCITT）
- Byte21：`Format`（u8，bit0=黑平面存在，bit1=红平面存在；MVP 固定 0x03）
- Byte22..31：预留（填 0）

> 头帧的 CRC8 仍然计算 `CMD|SEQ|FLAGS|DATA...`，STM32 在读完 Mailbox 一帧后需先验证 CRC8，再解析上述字段。

#### 7.4 数据帧（CMD=0x02, SEQ>=1）的 DATA 内容

数据帧 DATA 区仅承载图片字节流切片：

- Byte4..(4+len-1)：`ImageDataChunk`（原始图片数据的一个连续片段）

约定：

- `offset = (SEQ - 1) * ChunkSize`
- STM32 将本帧 ImageDataChunk 复制到：
  - `imageBuffer[offset .. offset + len - 1]`
- 若 `FLAGS.LAST_FRAME = 1`：
  - 说明这是最后一帧数据；
  - STM32 期望当前累计收到的总字节数 == `TotalBytes`。

图片整体 payload 在 RAM 中布局仍保持第 3 章约定：

- `imageBuffer[0 .. 3999]`：黑平面（1bpp）
- `imageBuffer[4000 .. 7999]`：红平面（1bpp）

#### 7.5 Android 发送侧流程（与现有架构对齐）

在 APP 端 NFC 模块中（例如新建 `EInkFtmImageSender`）：

1. **准备完整图片数据**
   - 已经通过三色化得到 8KB 图像 payload（Black 4KB + Red 4KB）。
   - 计算整包 CRC16‑CCITT。
2. **构造并发送头帧（Header Frame）**
   - 组装头帧 DATA 字段（Magic/Version/Width/Height/TotalBytes/...）；
   - 打包为 userPayload：`[CMD=0x01, SEQ=0, FLAGS=0, DATA..., CRC8]`；
   - 调用 `sendFtmData(nfcV, userPayload)`（外层 0xCA）。
3. **按 240B 切分图片数据并发送 Data Frame**
   - 以 `FTM_CHUNK_DATA_SIZE=240` 为单位将 8000B 拆分为 `TotalChunks` 个片段；
   - 对每个 `chunkIndex`（0..TotalChunks-1）：
     - `SEQ = chunkIndex + 1`；
     - `FLAGS.LAST_FRAME = 1` 仅在最后一帧置位；
     - DATA 区为对应的 `ImageDataChunk`；
     - 计算本帧 CRC8，封装 userPayload 后调用 `sendFtmData` 发送。
4. **MVP 阶段不强依赖 ACK**
   - 不设计复杂的帧级 ACK/NACK，只依赖：
     - Mailbox 写入的原子性；
     - 每帧 CRC8；
     - 整包 CRC16；
   - 若 `transceive` 抛异常或系统提示 Tag 丢失，直接中断本次发送并给出“请重新贴近重试”的提示。

#### 7.6 STM32 接收侧流程（FTM/Mailbox 视角）

STM32 侧与第 3.5 节整体思路保持一致，只是“数据来源”从 EEPROM Block 改为 Mailbox RAM：

1. **初始化**
   - 配置 ST25DV：
     - 使能 Mailbox/FTM；
     - 将 GPO 配置为 Mailbox 有消息时产生中断；
   - STM32 侧：
     - `MB_CTRL_Dyn` 写 `0x01` 打开邮箱；
     - 将 GPO 接至 EXTI 引脚（例如 `PA6`）。
2. **GPO 中断服务**
   - 中断函数中仅做：
     - 置标志 `g_mailboxHasData = 1`；
     - 快速返回。
3. **主循环 / NFC 任务轮询**
   - 若 `g_mailboxHasData == 1`：
     - 通过 I2C 一次性读出 Mailbox RAM 256 字节到 `mboxBuf[256]`；
     - 清 `g_mailboxHasData`；
     - 校验 CRC8：
       - 不通过：丢弃该帧，可选写错误码；
       - 通过：根据 `CMD` 分支处理：
         - `CMD=0x01 && SEQ=0`：按 7.3 中的格式解析头部，分配/准备 `imageBuffer`，记录 `TotalBytes/ChunkSize/TotalChunks/Crc16` 等；
         - `CMD=0x02 && SEQ>=1`：计算 offset，拷贝 ImageDataChunk 到 `imageBuffer` 对应位置，并更新“已收字节数/最后 SEQ”等本地状态。
4. **接收完成与刷屏**
   - 当已收数据长度达到 `TotalBytes` 且至少收到一帧 `LAST_FRAME=1` 的 Data Frame 时：
     - 对 `imageBuffer` 计算 CRC16，与头帧中的 `Crc16Ccitt` 对比：
       - 不匹配：放弃本次刷新，可选写错误状态；
       - 匹配：调用墨水屏驱动完成一次全屏刷新。

> 若后续需要更高可靠性，可在本协议上再叠加“简单 ACK 帧”（例如 STM32 通过 I2C 写控制区或反向 Mailbox 回复），MVP 阶段暂不引入。

- **是可以改成 FTM 协议的**，但这是一轮“重新设计传输层”的大改动：

### FTM 版整体协议设计（草案）

#### 1. 内存布局与角色分工

- **数据通道**：

  - 使用 ST25DV 的 **Mailbox RAM (256B)** 作为**唯一的数据通道**；
  - Android 每次最多写 256B 到 Mailbox；
  - STM32 只在 Mailbox 有数据时，通过 I2C 读出 256B。

- **控制信息（Control）**：两种可选放置方式
  - **方案 A（折中，推荐起步）**：
    - 继续使用当前 EEPROM 控制区 `0x0000`，结构维持 `EInkNfcProtocol.Control` 不变，只是语义调整为「FTM 会话控制」；
    - 这样 STM32 状态机改动最小（只把数据来源从 `DATA_ADDR` 换成 Mailbox），Android 也能复用大部分编码逻辑。
  - **方案 B（更彻底）**：
    - 控制字段也搬到 FTM 相关寄存器/FTM Mailbox 首几个字节；
    - 状态机会更简洁，但需要完全重写 STM32 的解析逻辑。
  - 先按 **方案 A**，后面再看要不要升级。

#### 2. FTM 版 Stop‑and‑Wait 流程（单向：手机 → STM32）

假设仍然三色 8KB，总共 `totalChunks = ceil(8000 / 256) = 32` 块。

**Android 端：**

1. **初始化控制区（同现在，只是“数据放在 Mailbox”）**

   - 写控制区（EEPROM）：
     - `session_id` 新值；
     - `width/height/format/totalBytes/chunkSize/totalChunks/crc16`；
     - `tx_state = IDLE`（你刚刚提的要求已经实现）；
     - `rxConsumedIndex = 0`。
   - 再写一帧：
     - `tx_state = SENDING`
     - `txChunkIndex = 0`
     - `txChunkLen = chunkSize`（先声明块大小）。

2. **对于每个 chunkIndex=0..totalChunks-1：**

   1. **等待 STM32 通知“上一块已消费”**
      - 轮询控制区（EEPROM）：读 128B 或只读前 32B；
      - 条件：`rxConsumedIndex == chunkIndex`（首块时已为 0，几乎秒过）。
   2. **写本块数据到 FTM Mailbox RAM**
      - 使用 ISO15693 的 FTM 命令，将当前 256B（或最后一块不足 256B）写入 Mailbox；
      - 可选：写入前几个字节存 `chunkIndex` / `len`（STM32 也可以不看，直接用控制区里的字段）。
   3. **更新控制区块字段**
      - 再写控制区（EEPROM）：
        - `tx_state = SENDING`；
        - `txChunkIndex = chunkIndex`；
        - `txChunkLen = len`。
      - ST25DV 内部会根据 Mailbox/控制区变化驱动 GPO（FTM 配置），stm32 通过 PA6 捕获“有新块”。

3. **收尾**
   - 所有块发送完成后，再写控制区：
     - `tx_state = DONE`（其它字段保持）。

**STM32 端：**

1. **空闲检测 / 会话开始（基本保持现在逻辑）**

   - 轮询控制区（或通过 FTM/GPO 检测），发现：
     - `magic/version` 正确；
     - `tx_state = SENDING`；
     - `session_id != g_last_session`。
   - 调用 `reset_session(session_id)`：清状态，`write_rx_state(RX_RECEIVING)`，`write_rx_consumed(0)`。

2. **块事件驱动（FTM/GPO + Mailbox）**

   - 当 ST25DV 通过 GPO（接 PA6）通知“Mailbox 有新数据”：
     - EXTI 中断里只置 `g_nfc_chunk_ready = 1`；
   - `NFC_Transfer_Poll()` 或主循环中：
     - 如果 `g_state == ST_RECEIVING && g_nfc_chunk_ready == 1`：
       1. 读控制区（EEPROM）：拿到 `txChunkIndex` / `txChunkLen` / `totalChunks`；
       2. 判断 `txChunkIndex == g_expected_chunk` 且 `txChunkLen` 合法，否则忽略；
       3. 用 I2C 读一次 Mailbox RAM 256B；
       4. 只取前 `txChunkLen` 字节：
          - 累计 CRC；
          - 流式写入 EPD RAM；
       5. `g_expected_chunk++`；  
          `write_rx_consumed(g_expected_chunk)`；
       6. 如果 `g_expected_chunk >= totalChunks`，则进入 `ST_VERIFY`。

3. **CRC 校验 + 刷屏**
   - 与现在 `ST_VERIFY` / `ST_APPLYING` 分支基本一致。
