# 2026-01-28-历史记录功能对比分析-plan

## 需求背景
用户要求再次检查 Android 端获取历史记录的功能，并与网页端 (`index.html`) 进行对比，确认是否存在区别。

## 对比分析

经过对 `MainViewModel.kt` (Android) 和 `index.html` (Web) 的详细代码审查，我们发现两者在核心逻辑上保持高度一致，但 Android 端在健壮性和细节处理上做了更多优化。

### 1. 核心逻辑 (一致)

| 功能点 | Web 端 (`index.html`) | Android 端 (`MainViewModel.kt`) | 结论 |
| :--- | :--- | :--- | :--- |
| **UUID** | `HISTORY_CHAR` (...23), `HISTORY_INFO` (...26) | `BleConstants` 中定义一致 | ✅ 一致 |
| **流程** | 读Info -> 停Notify -> 写时间戳 -> 启Notify | 读Info -> 停Notify -> 写时间戳 -> 启Notify | ✅ 一致 |
| **增量更新** | 取本地最大时间戳作为起始点 | 取数据库最新记录时间戳作为起始点 | ✅ 一致 |
| **数据包格式** | 12字节 (Time+Temp+Hum+Pressure) | 12字节 (Time+Temp+Hum+Pressure) | ✅ 一致 |
| **结束标志** | 单字节 `0xFF` | 单字节 `0xFF` (`BleConstants.HISTORY_END_FLAG`) | ✅ 一致 |
| **单位换算** | Temp/Hum: /100.0<br>Pressure: /100.0 (0.01hPa->hPa) | Temp/Hum: /100.0f<br>Pressure: /100.0f (0.01hPa->hPa) | ✅ 一致 |

### 2. 差异与优化 (Android 端更优)

| 功能点 | Web 端 | Android 端 | 说明 |
| :--- | :--- | :--- | :--- |
| **数据兼容性** | 仅支持 12 字节新格式 | **支持 12 字节和 8 字节旧格式** | Android 端增加了对不带气压数据的旧固件的兼容性。 |
| **异常处理** | 无自动全量重试逻辑 | **有自动全量重试逻辑** | Android 端若增量同步未获取到数据但设备有数据，会自动尝试全量同步 (Time=0)，防止因本地时间戳错乱导致无法同步。 |
| **进度计算** | 简单显示接收数 | **基于本地+增量计算总进度** | Android 端进度条显示更准确 (`dbCount + received` / `deviceTotal`)。 |
| **内存优化** | 全部加载到内存数组 | **分批写入数据库** | Android 端每满 20 条记录写入一次数据库并清空内存，防止大数据量 OOM。 |
| **排序显示** | 时间戳升序 (旧->新) | 时间戳降序 (新->旧) | Android 列表默认显示最新数据，符合移动端习惯。 |

### 3. 潜在细微差别 (已确认无风险)

- **气压类型解析**:
    - Web: `getUint32` (无符号)
    - Android: `getInt` 转 `Long` (处理无符号)
    - **结论**: 逻辑等效，无风险。

- **通知启动时序**:
    - Web: 添加监听器 -> 启动通知
    - Android: 启动通知 (异步回调中处理数据)
    - **结论**: Android 使用协程处理，确保线程安全，逻辑等效。

## 结论

Android 端获取历史记录的功能逻辑与网页端**完全一致**，并且在**兼容性**、**稳定性**（自动重试）和**性能**（分批入库）方面做了增强。

无需修改代码，目前的实现是正确且健壮的。
