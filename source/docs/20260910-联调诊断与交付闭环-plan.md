## 需求背景

上一轮（2026-09-08）完成了「启动自动连接最近设备」和「电池电压展示」的 App 侧实现，并通过单元测试与 Debug 构建。但交接文档明确留下了三类未闭环的问题：

1. **P0 —— 硬件协议未闭环**：App 已预留实时 8 字节、历史 14 字节解析，但没有任何手段确认固件是否真的按约定上报。此前只能依赖外部 BLE 抓包工具，联调门槛高。
2. **P1 —— 交付不完整**：只有 Debug 构建，Release 签名 APK 缺失，且项目没有任何签名配置入口。
3. **R4 —— 源码未纳入版本控制**：`source/` 在 Git 中仍是未跟踪目录，`git show HEAD` 只能看到 `README.md` 与 `src.zip`，后续接手者看不到逐文件差异。这是交接中最容易出错的点。

本轮目标是**在不依赖真实硬件的范围内，把这三类问题推进到可交接状态**：给 P0 提供联调抓手，给 P1 补齐构建与签名配置，给 R4 补齐版本控制。协议本身的最终确认仍需真实设备，不在本轮范围内。

## 实现方案

### 1. BLE 原始帧最小诊断（对应 P0）

新增 `data/bluetooth/BleFrameDiagnostics.kt`，作为**纯旁路观察**模块：

- 实时帧报出：帧长、是否含电压字段（含电压字段起始偏移）、十六进制预览。
- 历史帧报出：帧长、当前选中的记录格式名与单条记录字节数、完整记录数、尾部余字节、十六进制预览。
- 去重策略刻意保守：同一通道首次出现时报告一次，之后**仅当帧长变化时**再次报告。帧长变化恰是固件升级的关键信号，因此既不会刷屏，也不会漏掉关键转折。
- 断开连接时调用 `reset()`，使下一次连接重新报告一次基线帧长。

**关键约束：不改变任何协议判定行为。** 历史格式仍由 `DeviceProfile`/固件版本显式选择，绝不按帧长猜测；诊断只读取帧长与字节内容，不参与解析。

配套的小幅收敛：把解析器中的协议魔数提取为具名常量，使诊断与解析共用同一处定义，避免两处数字漂移。

### 2. 历史格式自述接口（对应 P0 / R2）

R2 的风险是「固件已变成 14 字节历史记录，却仍被识别为 V2，导致电压字段不被读取」。为让这一风险在联调时可被直接观测，新增 `HistoryFormatAware` 接口：

- 由 `HistoryDataParser` 实现，暴露 `historyFormatName` 与 `historyRecordSize`。
- `MainViewModel` 通过接口读取格式名，无需向下强转到具体实现。

这样日志中会同时出现「固件实际帧长」与「App 选中的格式」，两者不一致时一眼可见。

### 3. Release 签名配置（对应 P1）

`app/build.gradle.kts` 增加 `signingConfigs.release`，签名材料从仓库根目录的 `keystore.properties` 读取：

- 该文件已在 `.gitignore` 中排除，签名文件与口令都不入库、不进源码压缩包。
- 文件不存在时，`signingConfig` 为 `null`，release 变体退回**未签名构建**，`assembleRelease` 仍可用于编译验证。
- 提供 `keystore.properties.example` 模板说明字段与 `keytool` 生成方式。

本轮只做「可编译验证 + 配置入口」，不生成真实密钥。密钥一旦生成需用户自行保管，丢失将无法升级同名应用。

### 4. 源码纳入版本控制（对应 R4）

修正 `source/.gitignore`：

- 原规则只有 `/build`，会漏掉 `app/build` 等模块级产物；补上 `build/` 与 `**/build/`。
- 补充 `.kotlin`、`keystore.properties`、`*.jks`、`*.keystore`。

随后把 `source/` 完整纳入 Git，并在纳入前用精确路径校验确认没有构建产物与密钥混入。

- 本机**没有独立 JDK**，PATH 中无 `java`；唯一可用运行时是 Android Studio 自带 JBR，版本为 **JDK 25.0.2**。

**后续构建必须显式指定 JDK 17**，命令见下。不要用 Android Studio 的 JBR（JDK 25）直接跑 Gradle。

### 新发现的阻塞点：release 变体此前无法构建

仓库此前从未执行过 `assembleRelease`，因此一个**真实缺陷**一直被隐藏。首次执行时 `:app:lintVitalRelease` 直接失败，报出 235 条错误。

排查结论（错误全部同源，并非 235 个独立问题）：

- 全部 235 条都是 `InvalidFragmentVersionForActivityResult`，集中在 `MainActivity.kt` 的 `registerForActivityResult` 调用点。
- 用 `:app:dependencyInsight --dependency androidx.fragment --configuration releaseRuntimeClasspath` 追溯，根因是：

~~~text
com.google.android.gms:play-services-location:21.1.0
  └─ com.google.android.gms:play-services-base:18.1.0
       └─ androidx.fragment:fragment:1.0.0
~~~

本项目没有 appcompat/fragment 依赖，因此没有任何东西把 `fragment:1.0.0` 顶上去，它就一直停在 2018 年的 1.0.0，低于 `registerForActivityResult` 要求的 1.3.0。这不是 lint 误报，而是真实的依赖卫生问题。

**修复方式**：在 `app/build.gradle.kts` 的 `dependencies` 中加入版本约束，只提升下限、不新增直接依赖：

~~~kotlin
constraints {
    implementation("androidx.fragment:fragment:1.8.9") {
        because("play-services-base 传递依赖 fragment:1.0.0，低于 ActivityResult API 要求的 1.3.0")
    }
}
~~~

修复后解析结果确认为 `androidx.fragment:fragment:1.0.0 -> 1.8.9`，`lintVitalRelease` 通过。
